Three constraints that decide the design
Turo has no public API
Shut off Apr 2023; CarSync and Fleetwire were blocked with it. The extension in this repo is the only viable adapter — so the core must work when it is stale or gone.
Auto-send is an account risk
Automating a platform account is what Turo moved against. Ship Draft; the value is the merge, not the keystroke. Auto stays opt-in, per template.
GPS can't resolve side of street
ASP rules are side-specific; a Brooklyn street is ~11 m and consumer GPS errs 5–10 m. So: confirm the guess in one tap, cache the spot. A wrong-side alert that gets distrusted kills the feature.
The one abstraction that holds it together
Every module emits Task. The run sheet consumes nothing else. That keeps modules decoupled and lets cross-module rules live in one place.
Task { vehicle kind asp_move | turnaround trip_start | trip_end message | maintenance due_by location priority state }
Why it earns its place: a car out on a guest trip must not generate a street-cleaning alert. That suppression is one rule over Tasks — not four modules each learning about the others.

Build order: registry → telemetry → ASP. Then live on it for two weeks before building anything on top. Module 3 alone justifies the project.
Stack extends what is already here: FastAPI, plus Postgres with PostGIS (the one genuinely new piece of infrastructure — segment-and-side geo queries need it), APScheduler for deadline computation, a mobile-first PWA, MapLibre, and web push with SMS fallback for the parking alerts.
